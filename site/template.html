zram and zswap for MySQL: letting the InnoDB buffer pool grow past RAM

Can Linux compressed memory (zram, zswap) make an I/O-bound InnoDB workload faster by letting innodb_buffer_pool_size exceed what fits in RAM? Yes, by a lot, but only when the data compresses well and the frequently used data does not fit in RAM uncompressed.

The headline test

sysbench oltp_read_write, 64 threads, uniform access over 36 GB of tables (49 GB on disk), binary log off. The data was made compressible (~3× with lz4, ~6× with zstd) with sysbench-compressible: it cannot fit in the buffer pool uncompressed on this 31 GB server, but fits in RAM once compressed. 15 min warm-up + 10 min measured; every buffer pool was full of data during the measured window.

  • zram with lz4 is the clear winner: at a 40 GB pool all data stays in memory (InnoDB disk reads ~0/s), part of it compressed at ~3.3×. The server turns from I/O-bound into CPU-bound, and CPU per transaction is no higher than with disk I/O.
  • zswap trails zram (+93% vs +159%), and it is not the pool cap: raising max_pool_percent from 50 to 80 changed nothing at 40 GB (1,711 vs 1,698 tps). zswap keeps writing cold pages back to the swap disk (1–5k pages/s, the zswap shrinker is on by default in kernel 6.8), and every miss is a disk read; zram never touches the disk.
  • lz4 beats zstd once lz4 already fits the data: zstd compresses ~2× better but costs ~6× more CPU to decompress, and CPU becomes the limit. zstd is also less stable: its two runs at 40 GB differ by 11% (1,761 vs 1,563 tps), while every other repeated point is within 1%.
  • A plain swap file on a second SSD also helps (+40% at 40 GB): a fast swap device acts as an extra cache tier. Compression adds the rest.
  • Disk swap past the best size hurts: normal swap at 28 GB is slower than at 26 GB. Compressed swap made oversizing harmless in every round.

Why most benchmarks can't show this: page compressibility

The result depends on how well InnoDB pages compress. Each benchmark's data was loaded at small scale and every 4 KiB piece of its table files compressed on its own, the way zram and zswap do. Most OLTP benchmarks generate random strings, which lz4 barely compresses. Even real data sets reach only ~1.7×.

Compressed memory vs storage latency

Decompressing a page is far faster than reading it from any storage. Measured on this server's CPU (Xeon E3-1270 v6, one core) with real pages; storage figures are typical values except the last, measured under the benchmark load.

Compressing a 4 KiB page: 4.4 µs (lz4), 14 µs (zstd). The whole kernel path (reclaim, faults, compression) cost roughly 25 µs of CPU per page swapped out and back in.

Earlier rounds

HammerDB TPROC-C, 1000 warehouses (~93 GB)

Pages compress only ~1.25× with lz4. zram gained +10% at 32 GB and was OOM-killed beyond. zswap reached +21% at 40 GB, but the same swap file without zswap already gave +14%: most of the gain was the second SSD.

BenchBase AuctionMark (~86 GB)

CPU-bound, and the frequently used data (~23 GB) fit in RAM. Every setup tied (~7,500 req/s) and larger pools never filled. Compressed swap did make oversizing harmless; disk swap cost 13–22%.

zswap with a larger pool cap, zram with a disk fallback, zram writeback

zram capped at 12 GB of uncompressed pages (~3.6 GB of RAM) with the 2nd-SSD swap file as a lower-priority fallback (swapon -p 100 /dev/zram0; swapon -p 10 swapfile), with and without zram writeback of idle pages every minute; zswap with max_pool_percent 80 and 12 (12% ≈ the same compressed size as the capped zram).

  • This is a limited-memory simulation, not comparable with the uncapped zram run: the 12 GB cap gives zram ~3.6 GB of RAM where the uncapped device used ~6 GB, and leaves RAM unused. Compare it only with zswap at 12% (similar compressed budget). The fair test, growing the data set past what fits compressed with every setup uncapped, is round 5 (below).
  • zram with a lower-priority disk fallback works: no OOM, +77–105% over normal swap, but once zram is full the rest goes to disk (18–32k reads/s from the 2nd SSD).
  • With the same compressed size, zram + fallback beats zswap (1,566 vs 1,353 tps at 40 GB; 1,804 vs 1,322 at 44 GB).
  • zram writeback did not help on this uniform workload (1,536 vs 1,566): the pages it wrote out were read back about as fast. It needs a workload with a genuinely cold set.
  • zswap's gap to zram is not its pool cap: 80% instead of 50% changed little (1,711 vs 1,698 at 40 GB).

Other ways to compress (round 4)

The same 40 GB compressible data set and workload, compressing somewhere else: inside InnoDB, in the file system (ZFS keeps its read cache, the ARC, compressed), or with a compressing storage engine (MyRocks). Kernel swap is the host's normal 8 GB file throughout. Compare with normal swap at 26 GB (@BASE@ tps) and zram lz4 at 40 GB (@BEST@ tps).

  • InnoDB table compression (zlib) fits the data in the buffer pool but is slower than no compression: at 24–26 GB almost every read hits the pool (misses 0.03–0.08%), yet throughput stays at 650–710 tps. The time goes to writes: compressed tables log compressed page images to the redo log and write 3.7–4.6k pages/s, and pages are recompressed when changes no longer fit.
  • ZFS is slower than plain InnoDB in every configuration (280–578 tps). With 16K records on 4K sectors, a compressed record is stored in whole sectors, so lz4 reaches only 1.93× on this data (zram: 3.3×): the data does not fit in the ARC and reads stay on disk. zstd reaches 3.4–3.7× and serves 92–95% of the buffer pool's misses from the ARC, but runs out of CPU (56–61% kernel CPU): every ARC hit decompresses a 16K record again. ZFS itself also costs: with a normal 24 GB pool and a small 4 GB ARC it ran at 318 tps where ext4 ran at 794.
  • MyRocks with lz4 comes closest to zram: 1,940 tps with a 16 GB block cache (85% of zram's 2,286, same p95), the only alternative that does. Its data is 12 GB on disk (InnoDB: ~49 GB) and stays entirely in the Linux page cache, so there are no disk reads. A larger block cache hurts (24 GB: 1,442 tps, 19.5k reads/s) because uncompressed cache crowds the compressed files out of the page cache. zstd (6.7 GB on disk) is ~20% slower and CPU-bound. MyRocks uses more CPU per transaction than InnoDB (50–65% vs 42% per 1k tps), and it is a different engine, not a drop-in setting.
  • InnoDB page compression (lz4) saves disk (21 GB instead of ~49 GB) but halves throughput here (328 tps): the buffer pool holds uncompressed pages, so it is as read-bound as plain InnoDB, plus the cost of sparse files on every page write.

Setup

  • Bare metal: Intel Xeon E3-1270 v6 (4 cores / 8 threads), 31 GB RAM, 2 × 240 GB Intel SATA SSD. Ubuntu 24.04, kernel 6.8, Percona Server 8.4.11, binary log off.
  • Same server settings for every run; only the buffer pool size and swap setup change. Data restored before every run; clients on the same server.
  • zram: no disk swap, zswap off, priority 100. zswap: zsmalloc, max_pool_percent 50, 64 GB swap file on the second SSD. Compressed modes use vm.page-cluster=0, vm.watermark_boost_factor=0, vm.watermark_scale_factor=125, swappiness 180 (zram) / 100 (zswap).
